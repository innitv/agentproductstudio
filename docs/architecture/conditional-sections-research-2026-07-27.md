# Условная обязательность секций артефакта: как решать

Дата: 2026-07-27
Тип: доказательный ресёрч под решение
Метод: три параллельных сбора (агентные системы на GitHub / канонические механизмы схем / разбор нашего кода), синтез собран оркестратором

## 0. Задача

После смены умолчания на shadcn (`CLAUDE.md` §6.1) манифест требует Figma-секции на каждом запуске:

- `06-screens` → `## Layout Compiler Contract`, `## Figma Readiness`
- `08-frontend` → `## Design System Implementation`, `## Component Contract Implementation`, `## Frame / State Implementation Map`, `## Figma Visual QA Gate Summary`, `## Figma Roundtrip Deviations`

Боль измерена, а не предположена: прогон валидатора на реальном не-Figma запуске `outputs/contractor-payment-demo/2026-07-23` дал **10 ошибок** — пять по секциям, пять по JSON-схеме.

Нужно выразить «секция обязательна только на Figma-маршруте» так, чтобы:
1. отсутствие секции вне маршрута не было ошибкой;
2. отсутствие секции на маршруте оставалось ошибкой;
3. «намеренно пропущено» отличалось от «забыто» машинно, а не на доверии.

## 1. Что показал бенчмарк агентных систем

**Устоявшегося способа нет.** В агентных фреймворках (LangGraph 38k★, AutoGen/AG2, OpenHands 82k★, CrewAI 56k★, MetaGPT 69k★) единица контракта — вызов инструмента, а не «стадия с обязательными разделами документа». Условность выражается чем угодно, кроме схемы: разными типами шага, условной доступностью инструмента, условной строгостью при статичной схеме.

Отрицательный результат, важный сам по себе: **условной обязательности через JSON Schema `if`/`then`/`dependentRequired` нет ни в одном агентном фреймворке.** Strict-режимы провайдеров движутся в обратную сторону — LangChain и Agents SDK принудительно объявляют все поля обязательными.

В spec-driven инструментах (spec-kit 124k★, BMAD 51k★, agent-os, OpenSpec) условие пишется **фразой на естественном языке** в шаблоне и исполняется моделью, а не валидатором:

- BMAD v4: `condition: PRD has UX/UI requirements`
- spec-kit: `> **Fill ONLY if Constitution Check has violations**`
- agent-os: `IF spec_requires_database_changes: CREATE ... ELSE: SKIP this_step`

Проверяемость такого условия нулевая.

**Показательная эволюция:** BMAD в v6 **ушёл** от машинного `condition:` к явной норме трёх состояний — каждое измерение должно быть *decided* / *deferred (с условиями пересмотра)* / *open question*, и «целое измерение, оставленное в молчании, — это провал». Третье состояние снимает ложную дилемму «шум из N/A против потери проверки».

## 2. Что показали канонические механизмы

За пределами AI-инструментов задача давно стандартизована, причём одинаково в трёх независимых отраслях:

| Стандарт | Механизм |
|---|---|
| **OpenTelemetry semconv** | `requirement_level: conditionally_required: <текст условия>` — first-class поле модели |
| **DICOM PS3.5** | Type 1C / 2C: «имеют те же требования, что Type 1, при выполнении условий; когда условия не выполнены — **не должны включаться**» |
| **DITA / OASIS** | Profiling: фильтрация по атрибутам, профиль вынесен в отдельный файл DITAVAL |
| **HL7 FHIR** | `condition` + `constraint.expression`, с прямым предупреждением: без машинного выражения «валидаторы не смогут его применить» |

Общий каркас у всех один:

1. Уровень требования — не булев, а перечислимый.
2. Условие записано **рядом** с требованием, а не подразумевается.
3. Условие имеет **машинное выражение**, иначе валидатор его не исполнит.
4. Когда условие не выполнено, элемента **не должно быть** (Type 1C), а не «должен быть пустым» (Type 2) — это разные решения.
5. Неизвестное по умолчанию включается, а не выключается.

### Измеренный аргумент против «условия на каждом требовании»

Эксперимент на ajv 8.20 и zod 4.4.3 из нашего `node_modules`:

| Ситуация | `if`/`then` | Именованный профиль |
|---|---|---|
| Маршрут `figma`, секции нет | ошибка ✔ | ошибка ✔ |
| Маршрут `plain`, секции нет | пропускает ✔ | пропускает ✔ |
| **Опечатка `figmaa`** | **молча валидно** ✗ | ошибка ✔ |

`if` не является утверждением сам по себе: не совпало — `then` просто игнорируется, без сообщения. Любая опечатка, переименование или новый маршрут **тихо отключают все требования разом**.

Индустрия прошла это на практике: Kubernetes удалил пополевую PodSecurityPolicy в пользу трёх именованных профилей, и причина сформулирована прямо — «часто было непонятно, какая политика применилась к объекту». Тот же паттерн профилей у ESLint, mypy (`--strict`), Spectral, ansible-lint (`min → … → production`).

### Формула различения «пропущено» и «забыто»

Собрана из живых инструментов:

| Инструмент | Как оформляется пропуск | Как ловится протухший пропуск |
|---|---|---|
| **mypy** | `# type: ignore[код]` | `warn_unused_ignores` — ненужный ignore становится ошибкой |
| **ESLint** | `// eslint-disable-next-line rule -- причина` | `reportUnusedDisableDirectives`, дефолт `warn` |
| **pytest** | `@mark.skipif(cond, reason=...)`, reason обязателен | `xfail(strict=True)` — если помеченный тест **прошёл**, падает прогон |
| **GitHub Actions** | статус `skipped` | ❌ **нет**: skipped считается success и не блокирует merge |

Провал GitHub Actions задокументирован на живом проекте (Pantsbuild): фильтр по путям даёт вечно-pending чек, а условие `if:` — тихий ложный успех. Их решение — превратить факт осознанного пропуска в **положительный артефакт**, который проверяется машинно.

## 2.1. Что показали движки данных и workflow

Отдельный кластер (Dagster 15.9k★, great_expectations 11.7k★, Prefect 23.5k★, Kedro 10.9k★, Temporal 21.9k★, плюс смежные dbt, soda-core, Airflow) дал два механизма, которых нет ни в агентных системах, ни в схемных стандартах.

**Двухфазный ledger обещаний — Dagster.** Событие «проверка запланирована» пишется **до** исполнения, и незакрытое обещание резолвится в отдельный статус:

```
AssetCheckExecutionResolvedStatus:
  IN_PROGRESS · SUCCEEDED · FAILED · EXECUTION_FAILED
  SKIPPED  # run закончился, не упал, но проверка не выполнилась
```

Это **единственный найденный механизм, где «забыли» видно машинно без специальной аннотации**. Плюс прямая формулировка границы в докстринге `blocking`: «гейт применяется только к *провалившимся* результатам; если результат не выдан вовсе, downstream выполняется, а факт логируется предупреждением».

**Легитимность пропуска — свойство спецификации, а не рантайма.** У Dagster `skippable` объявлен в самой спеке ассета и превращается в `is_required=False`. Если выход не объявлен опциональным и не выдан — жёсткая ошибка `DagsterStepOutputNotFoundError`. То есть «не обязателен по объявлению» и «не выдан по забывчивости» разведены на уровне типа.

**Богатая таксономия исхода вместо булевой — soda-core:**

```
CheckOutcome: PASSED · FAILED · WARN · NOT_EVALUATED · EXCLUDED
```

Где `NOT_EVALUATED` = «не смогли измерить», `EXCLUDED` = «исключена отбором». Отбор декларативен через селекторы по типу, колонке, атрибутам.

**dbt** — единственный, у кого условность и серьёзность объявлены рядом в конфиге проверки: `enabled`, `where` (применимость по данным), `warn_if` / `error_if` (серьёзность по величине нарушения), и всё это доезжает до отчёта статусами `TestStatus{Pass, Error, Fail, Warn, Skipped}`.

**Главный отрицательный вывод кластера:** ни один из проверенных движков не различает «неприменимо» и «забыли» полноценно. Ближе всех Dagster (PLANNED→SKIPPED плюс `skippable` в спеке) и soda-core (`NOT_EVALUATED` против `EXCLUDED`). У great_expectations осознанный пропуск уходит только в отладочный лог, у Prefect статус `SKIPPED` вообще **удалён** при переходе с 1.x на 2.x, у Temporal контракта результата нет по конструкции.

## 3. Что показал разбор нашего кода

**Условность в архитектуре уже есть, но не для секций.** Рядом с плоским `requiredSectionsByArtifact` (`workflow.manifest.ts:62`) живут `requiredArtifactsByProfile` (:61) и `scales` на стадии (:67).

**Профиль `standard`/`reference` использовать нельзя.** Это ось «reference-driven или нет», а не «Figma или нет»: reference-задача бывает и с Figma, и без. Авторы кода сами описали эту ошибку в комментарии про `scale` (`manifest:7-17`). Бинарность профиля зашита в 12 местах.

**Эталон для копирования — механизм `scale`:**

- декларация на элементе (`stage.scales`);
- фильтрующий хелпер (`getWorkflowStagesForProfile`);
- **явный список пропущенного** (`getStagesSkippedByScale`) с комментарием «молчаливый пропуск неотличим от забытой стадии»;
- **чтение из persisted state, а не угадывание**: `validate-workflow-run.ts:61-64` — «Масштаб берётся из run-state, а не угадывается по содержимому: иначе неполный run выглядел бы как честный маленький»;
- **anti-backdating gate** (:233-247) — занижение масштаба задним числом = ошибка.

**Проверка секций сейчас наивная:** `content.includes(section)` (`validate-workflow-run.ts:104-112`). Поэтому `### Заголовок` проходит гейт на `## Заголовок`, а заголовок с текстом `not_applicable` неотличим от честно заполненной секции.

**`not_applicable` — соглашение, а не проверка.** Формулировка «заполняются как `not_applicable`, но не удаляются» повторена в четырёх контрактах; валидатор про это слово не знает вообще. Но на уровне данных это уже легальная сущность: `screens.schema.json` содержит `figma_layout_ir_required: boolean` и `layout_ir_status: not_required` — то есть «Figma тут не было» уже выразимо честно.

**Цена по тестам известна точно:** сломается один тест (`test-agent-output-skeletons.ts`), две ошибки в двух файлах. Побочная находка: `test-workflow-validator.ts` контракт секций **вообще не защищает** — его фикстуры намеренно уже манифеста.

## 4. Рекомендация

**Ввести третью ось запуска по образцу `scale`, выраженную именованными значениями, а не условиями.**

Почему не альтернативы:

- **Условие на каждом требовании** — измеренная дыра с опечаткой (§2), плюс третий несогласованный механизм поверх двух существующих.
- **Расширение профиля `standard`/`reference`** — смешивает две ортогональные оси, ошибка того же класса, что авторы кода описали для `scale`.
- **Детекция по наличию `figma-layout-ir.json`** — ровно то, что запрещено прецедентом `scale`: Figma-запуск, не создавший файл, выглядел бы как честный не-Figma и обошёл гейт.

Конструкция, все элементы проверяемы машинно:

1. **Закрытый перечень значений оси**, валидируемый отдельно от требований. По измерению — единственный способ получить одну внятную ошибку на опечатку вместо мусора.
2. **Значение фиксируется на `00-intake` и читается из `run-state.json`**, флаг командной строки — только для перепроверки. Копия того, как сделан `scale`.
3. **Валидатор не спрашивает** секцию вне маршрута, а не прощает её отсутствие. Сужение до генерации сильнее прощения после — паттерн из MetaGPT (`exclude` полей), OpenHands (`create_action_type_with_risk`), AutoGen (`update_conditional_functions`).
4. **Пропуск — положительная запись** с причиной из закрытого перечня, в `stage-gate-ledger.md`. Наш `skipped_with_reason` — уже правильная форма, бенчмарк это подтверждает.
5. **Две обратные проверки на сами записи** — без них любая схема деградирует через год:
   - запись «пропущено» для секции, которая **входит** в набор текущего маршрута → ошибка (модель `xfail(strict=True)`);
   - запись «пропущено» для секции, которой нет **ни в одном** маршруте → ошибка (модель `warn_unused_ignores`).
6. **Anti-backdating** по образцу `scale`: смена маршрута после того, как стадии отработали, — ошибка.

### Решение, которое нельзя принять молча

**Дефолт для запусков без поля.** У `scale` дефолт `full` = «как было раньше», обратная совместимость бесплатна. Здесь «как было» = Figma-маршрут, а фактическое умолчание — код.

Рекомендую: **отсутствие поля читать как Figma-маршрут** (строгий вариант), новые запуски получают значение явно на intake. Иначе все исторические запуски задним числом освобождаются от проверок, которые проходили.

### Чего у нас нет и что стоит взять

**Двухфазный ledger по образцу Dagster** — самая ценная находка. Сейчас `stage-gate-ledger.md` фиксирует пропуск *постфактум*, когда стадия отработала. У Dagster обещание пишется **до** исполнения, и незакрытое обещание само становится видимым статусом. Применительно к нам: на intake фиксируется, какие секции ожидаются на этом маршруте, а незаполненная ожидаемая секция резолвится в отдельный статус, а не проваливается в общую ошибку.

**Третье состояние из BMAD v6** — `deferred` с условием пересмотра вместо дилеммы «писать N/A или удалить».

**`warn` вместо удаления правила** там, где применимость неочевидна. Прямая цитата ansible-lint: «мы **не рекомендуем** `skip_list`, потому что он скрывает нарушения из вывода». Тот же принцип у Dagster (`WARN` не блокирует, но остаётся в отчёте) и soda-core.

**Понижение вместо падения** для результата вне контракта: Dagster превращает неожидаемый результат проверки в наблюдение с предупреждением, а не в ошибку. Для нас это про секцию, которая появилась, хотя маршрут её не требует, — это не повод валить run.

## 5. Границы доказательности

Подтверждено первоисточниками: спецификации OTel semconv, DICOM PS3.5, DITA, FHIR, JSON Schema; исходники и шаблоны spec-kit, BMAD, agent-os, OpenSpec, MetaGPT, CrewAI, LangGraph, OpenHands; пути и строки нашего кода; измерения на ajv 8.20.0 и zod 4.4.3.

**Не подтверждено, не выдаётся за факт:**
- нормативный текст JSON Schema 2020-12 §10.2.2 — четыре источника дали 404 или усечение; семантика опирается на документацию json-schema.org, документацию Ajv и измерение;
- Schematron `phase` — только вторичные источники, стандарт за пейволом;
- числовые лимиты стоимости CEL в Kubernetes;
- Dify, Flowise, n8n — пути в репозиториях изменились, по коду не проверены;
- `pydantic` `Discriminator`/`Tag` и исходники Dagster `asset_check_spec.py` — читались по документации, не по коду.
