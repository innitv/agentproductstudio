## 2. P0 — требуют решения

### P0-1. Гейт «человек утверждает макеты» на дефолтном маршруте не работает

`README.md:114` обещает безусловно: «frontend не начинается, пока человек не утвердил макеты». В `CLAUDE.md` правила нет — там требование о *наличии артефактов*, а не о согласии человека.

Единственная письменная форма — `claude-operating-rules.md:225`, пункт 7 списка **«Обязательный порядок reference-scan и Figma write»**. Весь список — про reference-driven задачи с Figma. На дефолтном маршруте (`track: code`, профиль `standard`) он не читается.

Машинной опоры нет: в `approval-gate.ts:6-19` двенадцать действий, утверждения дизайна среди них нет; в `approval-matrix.md` строки нет.

Гейт держится на личном `~/.claude/CLAUDE.md` — файле вне репозитория, невидимом для тестов и других пользователей.

### P0-2. Маршрут меняется задним числом через штатную команду

`CLAUDE.md` §0.3 обещает: «Маршрут нельзя сменить задним числом». `validateTrackGates` (`validate-workflow-run.ts:439-473`) ловит только **расхождение** `run-state.json` ↔ `run-meta.json`. `yarn workflow:sync` переписывает оба согласованно (`sync-run-state.ts:69, 117`) — сигнал исчезает.

Доказано прогоном на копии завершённого run (стадии 06 и 08 = `completed`):

| Шаг | Ошибок |
|---|---|
| как записан (`figma`) | **19** |
| `sync --track code` + дописанные строки `skipped_by_track` | **9** |

Ни одной ошибки anti-backdating. Занижение `scale` защищено правильно — `validate-workflow-run.ts:334-348` смотрит на **фактические статусы стадий**, а не на согласие двух файлов. Это готовый образец для починки.

### P0-3. Ось `profile` угадывается по тексту — на реальном run это скрыло 7 ошибок

`validate-workflow-run.ts:76-78` вычисляет профиль регулярным выражением по тексту (`/reference_url\s*:/`, `/как этот сайт/`) **до** чтения `run-state.json` и никогда к нему не обращается. Расхождение — только warning.

Факт на единственном полном run:

```
WARN: run-state.json profile is 'reference', but validation profile is 'standard'
→ 19 errors, 5 warnings

тот же run с явным --profile reference:
ERROR: 09-visual-reference: missing required visual-diff-result.json evidence
→ 26 errors, 6 warnings
```

Все три источника (`run-state.json`, `run-meta.json`, шапка ledger) говорят `reference`. Гейт визуальной сверки не исполнялся.

Дефект **известен**: `agent-output-critic.ts:391-396` описывает его с теми же числами и обходит, передавая `--profile` явно. Корень не починен — прямой вызов CLI, предписанный `CLAUDE.md` §10, дефект получает. Хуже: `run-ledger/SKILL.md:29`, `qa.md:11`, `stage-gate-ledger.template.md:23` подсказывают `--profile standard`.

Соседний модуль решает ту же задачу правильно: `sync-run-state.ts:60` — `options.profile ?? previousState?.profile ?? detectProfile(...)`.

### P0-4. QA определяет Figma-ветку запрещённым способом

`.claude/agents/qa-review.md:23`, `qa-review.agent.md:99,100,172` — «Figma-аудит применяется только к задачам, реально прошедшим Figma-ветку (есть `figma-layout-ir.json`/`figma-handoff-bundle.md`)».

Запрет дословно: `run-ledger/SKILL.md:53` — «определять его по наличию `figma-layout-ir.json` **запрещено**: Figma-run, не создавший файл, выглядел бы как честный код-маршрут». Тот же запрет в `validate-workflow-run.ts:84-86`, `frontend.agent.md:211`.

Слово `track` в обёртке и контракте QA не встречается **ни разу** (`grep -c` → 0/0).

Следствие: `figma_layout_ir` не производится ни одним маршрутом. На `track=figma` запуск, не создавший IR, не остановят ни валидатор, ни QA — QA сам пометит гейты `not_applicable`. **Ось `figma` не имеет исполнителя проверки.**

### P0-5. Второй вход в Figma-ветку в обход ответа человека

`.claude/agents/orchestrator.md:44` и `design.agent.md:45`: «Figma-ветка включается по явному запросу **или обоснованному `product_specific|bespoke`**».

`design_system_mode` выбирает агент на 04-design; ответ человека даётся на 00-intake и пишется в `run-state.json`. Решение агента на четвёртой стадии переопределяет ответ человека на нулевой. При этом обратный ход закрыт: смена `track` после отработки 06/08 — error. Текст предписывает путь, которого в машине нет.

Там же: скаффолд не знает про `scale` и `track` вовсе (`workflow-engine.ts:53` передаёт только `goal` и `profile`) — run-plan перечисляет все 13 стадий независимо от масштаба, полей `Track`/`Scale` и таблицы «Секции вне маршрута» нет.

### P0-7. Глобальные копии навыков перебивают проектные

В `~/.claude/skills/` лежат **реальные каталоги** `landing-builder` и `visual-diff-verifier` — тогда как `figma-ds` и `subsystem-audit` рядом сделаны симлинками на проект.

Глобальная копия выигрывает коллизию имён: в листинге навыков сессии стоит её описание. Проектная версия не доезжает никогда.

Расхождение по главному сигналу маршрутизации:

| Источник | Описание |
|---|---|
| глобальная (роутер видит её) | «bespoke-реализация… вёрстка с нуля… применяется, если проект не объявил свою DS» |
| проектная (мёртвый текст) | «для product UI по умолчанию из компонентов shadcn/ui» |

Тело глобальной само уступает проекту («проектный `CLAUDE.md` > этот skill»), но описание читается **до** тела. По собственному условию навык в этом репозитории применяться не должен — а `yarn workflow:skills` ставит его первым для `08-frontend`.

Причина утечки machinery: `skill-metadata.ts:120-163` намеренно **не требует** равенства описаний зеркал (комментарий в коде).

Плюс: проектный `landing-builder` привязан к стадии `08-frontend` и является частью пайплайна, глобальный — переносимая процедура. **Это разные сущности с одним именем.**

Каждая находка верифицирована первоисточником: путь, строка, где применимо — вывод команды. Прогоны выполнялись на копиях в изолированных каталогах, рабочее дерево не изменялось.

Не проверено: семантика поля `effort` в обёртках агентов (стоит на 5 из 13, в runtime не читается) — как находка не подаётся. Четыре из пяти реальных каталогов `outputs/` — неполные run без `run-state.json`, они не нагружают новые механизмы; настоящую проверку легаси даёт один `contractor-payment-demo`.
