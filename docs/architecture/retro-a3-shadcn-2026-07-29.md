## 3. Пять находок

### Находка 1. Метрики ретро слепы к тому, ради чего ретро существует

`found_by` определяется эвристикой по заголовкам заходов, а сами заходы — по датированным
`##`-заголовкам в артефактах. Ни один агент разметку `<!-- retro: … -->` не поставил, и
ни один не оформлял правку отдельным датированным заходом: `frontend-result.md`
переписывался целиком. Итог — нули по всем осям при девяти фактических возвратах.

Порог §5 «хотя бы одна находка `user_device`» **не сработал**, хотя таких находок было
восемь. Порог, который не срабатывает на своём главном случае, не защищает.

**Решение: норма в контракте.** Разметка захода перенесена из рекомендации в обязанность
исполнителя стадии: правка по внешнему замечанию оформляется отдельным датированным
`##`-заходом с `<!-- retro: pass=N found_by=… -->`. Машинную проверку здесь построить
нельзя — канал находки не выводится из артефактов, в этом вся его природа; но норма
адресуется тому, у кого информация в руках в момент правки.

### Находка 2. Восемь расхождений с образцом прошли четыре зелёные машинные приёмки

`vr:test` 95/0, `test-storybook` 64/0, `qa:mobile` 5/0/0, axe 0 нарушений — и при этом
серые кнопки и поля, лишние тени на кнопках и полях, зазор 32 вместо 12, переименованный
пункт меню, выдуманное состояние «файл готовится» на месте активных ссылок.

Причина структурная: **визуальная регрессия сравнивает рендер с собственным эталоном**,
снятым с той же реализации. Расхождение с внешним образцом она не видит по устройству —
эталон и реализация всегда согласованы между собой. Три главные находки стадии
`09-visual-reference` тоже пришли из ручного измерения, а не из гейта.

**Решение: осознанный отказ с причиной.** Автоматическая сверка с Figma-образцом
(рендер против экспортированного кадра) на этом маршруте не строится: макет и вёрстка
различаются легитимно — шрифтовый рендеринг, сглаживание, принятые отклонения. Порог
диффа, терпимый к этому, пропустит и найденные дефекты. Отказ фиксируется вместе со
следствием: **для reference-driven задач гейт человека обязателен и незаменим машиной** —
это записано в `claude-operating-rules.md` §6 вместе с измеренной ценой.

### Находка 3. Генератор стадии создаёт фиктивный артефакт, sync считает стадию выполненной

`workflow:start` создал `design-brief.md` со `status: "ready"`, готовым
`visual_direction` про «сдержанный продуктовый лендинг» и `inputs_used`, перечисляющим
`prd.md`, `ia-brief.md`, `research-summary.md` — артефакты стадий, **вычеркнутых
масштабом**. Затем `workflow:sync` увидел файл на диске и перевёл `04-design` в
`completed`.

Run стартовал с фиктивно закрытой стадией дизайна. Не заметь этого оркестратор —
дизайн-агент не запустился бы вовсе, а `05-copy` и дальше работали бы поверх текста,
ссылающегося на несуществующие входы.

**Решение: машинная проверка.** Тест `test-scaffold-no-fiction`: сгенерированный до работы
стадии артефакт не имеет права нести `status: ready` и `inputs_used`, ссылающийся на
артефакты стадий вне масштаба run. Негативный контроль и уточнение диагноза — в §4.

### Находка 4. Стадии молча правили образец

Два случая, оба вскрылись только при просмотре человеком:

- `06-screens` переименовала пункт меню «Документы» → «Раскрытие информации», записав
  довод «два термина для одного места — расхождение, а не краткость»;
- `06-screens` и `08-frontend` заменили шесть активных ссылок на документы состоянием
  «Файл готовится», которого в образце нет, потому что PDF ещё не выгружены.

Оба решения разумны по существу и оба меняют образец. В reference-driven run образец —
источник истины, а его правка — продуктовое решение заказчика, не стадии.

**Решение: норма в контракте.** В `design-generator.agent.md` и `frontend.agent.md`:
отступление от образца фиксируется в отчёте стадии отдельной строкой
`reference_deviation` с указанием, что в образце и что сделано вместо, и эскалируется
оркестратору. Молчаливое «мы решили лучше» — `process_deviation`.

### Находка 5. Знание записывается не на тот уровень

Правило «`shadow-xs` зашит во все интерактивные примитивы реестра» было записано
комментарием внутри `apps/frontend/src/styles/a3.css` — то есть внутри продукта.
Следующий продукт этот файл не прочитает, и грабля повторится. Нашёл пользователь
вопросом «а если я буду другие макеты собирать — откуда ты это вспомнишь».

Механизм ошибки: знание записывается там, где идёт правка, а не там, где его будут
искать. Тот же механизм породил `token-map.md`, описывавший 28 % реальности.

Существующие сторожа против расползания инструкций такое не ловят: запись формально
корректна и лежит в валидном файле.

**Решение: норма в skill.** В `run-ledger` добавлено правило записи: перед фиксацией
знания ответить, **кто прочитает его в следующий раз** — про библиотеку → `CLAUDE.md`
§6.1, про процесс → `claude-operating-rules.md`, про продукт → рядом с продуктом.
Знание о библиотеке в продуктовом файле — дефект размещения, даже если текст верен.

## 4. Негативный контроль механизма из находки 3

Тест `runtime/typescript/test-scaffold-no-fiction.ts`, команда
`yarn workflow:test-scaffold-no-fiction`, включён в агрегатор `workflow:test-agentic`.

**Фактический вывод падения на неисправленном коде:**

```
FAIL scaffold-no-fiction
  design-brief.md: payload status 'ready' в сгенерированном артефакте
    (стадия ещё не выполнялась — допустим только 'pending'/'partial')
  design-brief.md: inputs_used ссылается на 'research-summary.md',
    'scenario-user-flows.md', 'prd.md', 'ia-brief.md' — артефакты стадий
    вне масштаба 'increment'
```

После исправления — `scaffold no-fiction tests passed`, `typecheck` зелёный, тест убирает
за собой созданный каталог.

**Что исправлено в `run-local-workflow.ts`:**

- `const status = isResearchPartial ? "partial" : "ready"` → добавлена проверка
  `hasResearch`: отсутствие артефакта больше не читается как готовность;
- захардкоженный `inputs_used` заменён фильтром `existingInputs()` по факту
  существования файла в каталоге run.

### 4.1. Первая версия теста проходила вхолостую — и это часть результата

Исходный тест проверял каталог сразу после `runLandingWorkflow` и **прошёл**. Причина:
скаффолд `design-brief.md` не создаёт вовсе, файл пишет генератор downstream-артефактов
при выполнении стадии. Сработала ветка «файла нет — проверять нечего», и зелёный ничего
не значил.

То есть мой первоначальный диагноз находки 3 («скаффолд создаёт фикцию») был неточен:
фикцию создаёт `buildLocalDownstreamArtifacts`. Тест переписан на реальный путь, ветка
«файла нет» заменена жёстким `assert` — теперь отсутствие артефакта роняет тест как
недостоверный, а не молчаливо засчитывает успех.

Это иллюстрация к находке 2 в миниатюре: **зелёная проверка и отсутствие проверки
выглядят одинаково**, различить их можно только негативным контролем.

## 5. Что НЕ пошло в находки

- **`workflow:start` уводит цель в парсер намерений.** Цель со словом «макет» подцепила
  чужой существующий run вместо создания нового. Это баг маршрутизации, а не дефект
  процесса — заведён отдельно, ретро его только зафиксировало.
- **`qa:mobile` был настроен на чужой маршрут** и дал бы ложное «пройдено». Поймала
  стадия `06-screens` до вреда — механизм сработал, разбирать нечего.
- **Правка общих примитивов ради одной темы разъехала чужой экран.** Поймала сверка,
  фронтенд починил откатом причины, а не подгонкой. Цикл отработал как задумано.

## 6. Что подтвердилось хорошего

Цепочка трижды поймала себя сама: сверка опровергла заявление фронтенда о «чистом

кроме одного случая с тенью панели — и его поймала следующая стадия.

Открытая проверка из памяти закрыта: **pipeline после сокращения студии работает**.
