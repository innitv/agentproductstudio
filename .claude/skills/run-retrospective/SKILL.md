# Skill: Run Retrospective (Разбор Завершённого Запуска)

## 1. Назначение

Разбор завершённого run — это способ превратить один дорогой запуск в правила, которые
переживут сессию. Прецедент: ручная ретроспектива `contractor-payment-demo`
(2026-07-23…25) дала 20 находок аудита согласованности, четыре системных теста и две
новые обязательные нормы. Она делалась руками, и без этого skill повторилась бы только
случайно.

**Главное ограничение — стоимость.** Процедура, требующая получаса подготовки, не
переживёт двух run. Поэтому разбор устроен так: одна команда собирает числа, человек
тратит время только на интерпретацию, и результат ограничен пятью находками.

## 2. Когда применяется

- Run закрыт (`12-release` завершён или run осознанно закрыт как `partial`).
- Run был содержательным: есть хотя бы один повторный заход, отклонение процесса или
  находка, пришедшая от пользователя. Run без единого возврата разбирать нечего —
  запиши это фактом и остановись.
- Run закрыт как `blocked`/`failed` — разбирать **обязательно**, независимо от размера.

Не применяется к `outputs/temp/**` и к чужим архивам «на посмотреть».

## 3. Порядок работы

Ориентир по времени — 20 минут. Больше значит, что разбор превратился в аудит; аудит —
это `/subsystem-audit:audit`, другой маршрут (см. §7).

1. **Собери числа.** `yarn workflow:retro outputs/<slug>/<YYYY-MM-DD>`. Команда читает
   `run-state.json`, `run-meta.json`, `stage-gate-ledger.md`, `stage-results/*.json` и
   markdown-артефакты стадий. Ничего не пишет: закрытый run — read-only.
2. **Прочитай раздел «Чего эти числа не видят» первым.** Он печатается всегда. Разбор,
   начатый с таблицы метрик, systematically переоценивает полноту картины.
3. **Пройди пороги §5.** Каждый сработавший порог даёт кандидата в находки.
4. **Отбери не больше пяти находок** по цене канала: сначала то, что нашёл пользователь
   на устройстве, потом отклонения процесса, потом циклы правок, потом косметика.
5. **Закрой каждую находку одним из трёх решений** (§6). Находка без решения —
   это заметка, а не результат; через два run её не найдут.

## 4. Метрики и что каждая означает

Все пять вычисляются из артефактов без ручного ввода — метрика, требующая ручного
ведения, не ведётся. Фактические значения для `contractor-payment-demo` приведены как
калибровка «как выглядит тяжёлый run».

| Метрика | Что означает | Тот run |
|---|---|---|
| Повторных заходов | Возвраты к уже сделанному сверх первого прохода. Считается по датированным `##`-заголовкам в артефактах стадий | 11 (из них 9 в `08-frontend`) |
| Дорогих находок | Заходы с каналом `user_device`/`user_review`: нашёл пользователь, а не проверка | 3 распознано, реально больше — см. §4.1 |
| Отклонений процесса | Строки таблицы `## Process Deviations` в ledger | 7 |
| Approval задним числом | Строки approval с признаком «постфактум/восстановлено»: внешнее действие сделано раньше записи | 3 из 15 |
| Долг валидатора на закрытии | Число errors в последнем прогоне валидации, записанном в ledger | 26 |
| Слепых зон ledger | Завершённые стадии с пустым `inputs_used` плюс стадии, где `attempts` меньше числа заходов | 5 |

### 4.1. Канал находки — единственное, что требует разметки

Кто нашёл проблему, машинно из артефактов не выводится. Команда определяет канал
эвристикой по тексту заголовка захода и **всегда помечает это как эвристику**. На том run
эвристика распознала 3 захода из 13 — остальные заголовки («Правки экранов банка
O-2/O-3») источник не называют.

Разметка — одна строка сразу под заголовком захода:

```
## Правки по фидбэку с живого демо (2026-07-24)
<!-- retro: pass=6 found_by=user_device -->
```

Значения `found_by`, от дешёвого канала к дорогому: `validator`, `agent_self`, `qa`,
`orchestrator`, `user_review`, `user_device`.

Ставит её тот, кто делает заход, в момент захода — тогда информация ещё в руках.
HTML-комментарий выбран намеренно: секции артефактов задаются
`requiredSectionsByArtifact` в `runtime/typescript/workflow.manifest.ts`, и любое
добавление туда рассинхронизирует скелеты в промптах агентов — этот класс уже стрелял
(P0-1 аудита согласованности 2026-07-25).

## 5. Пороги: когда число обязано превратиться в разбор

| Порог | Что разбирать | Чего НЕ делать |
|---|---|---|
| Заходов на одну стадию > 3 | Вход стадии: что она не получила на первом проходе. На том run `08-frontend` получил 10 заходов при пустом `inputs_used` — это про полноту Delegation Packet | Не сводить к качеству исполнителя. Десять заходов у одной стадии — это признак того, что решение принималось по ходу, а не до |
| Хотя бы одна находка `user_device` | Какая автопроверка поймала бы её до пользователя. Если никакая — записать, почему её нельзя построить | Не записывать «будем внимательнее». Внимательность не воспроизводится |
| Approval задним числом > 0 | Что сделало запись невозможной вовремя (нет TTY, действие выполнял владелец в своём окружении, шаг не был предусмотрен) | Не считать это согласием: дефицит был в записи, а не в разрешении — но и не считать формальностью |
| Долг валидатора на закрытии > 0 | Причина каждой группы ошибок. На том run 25 из 28 были одного класса «скелет промпта отстал от манифеста» — это чинится один раз тестом, а не в каждом run | Не закрывать run с необъяснённым остатком: непрочитанные ошибки неотличимы от забытых |
| Стадия завершена с пустым `inputs_used` | Дисциплину ledger, не стадию. Пустой список означает, что не видно, на чём стояло решение | Не дописывать `inputs_used` задним числом в закрытый run |
| `attempts` меньше числа заходов | Правки шли мимо движка. Пока это так, статистика повторов недостоверна по всем run | Не «чинить» цифру в `run-state.json` вручную |

## 6. Три решения, и других нет

Каждая находка закрывается ровно одним:

1. **Машинная проверка** — тест или валидатор. Предпочтительно всегда, когда правило
   формулируется как «X обязан совпадать с Y». Эвристика проекта: всё, что не
   проверяется машиной, дрейфует обязательно.
2. **Норма в skill или контракте** — когда правило про суждение, а не про совпадение
   (например «мобильная приёмка ведётся в профиле устройства»). Норма живёт в ОДНОМ
   месте, остальные документы ссылаются.
3. **Осознанный отказ с причиной** — когда цена механизма выше цены проблемы. Причина
   записывается; «не успели» причиной не является.

Находка, для которой ни одно из трёх не выбрано, из отчёта удаляется. Список
незакрытых наблюдений — это то, что делает ретро ритуалом.

**Новый механизм — с негативным контролем.** Тест, который не показали падающим на
сломанном коде, не доказан. Приложи фактический вывод падения, а не утверждение.

## 7. Границы

- **Ретро ≠ аудит подсистемы.** Ретро читает хронику одного run: что происходило и в
  каком порядке. Расхождения вида «правило заявлено, код его не исполняет» — предмет
  `/subsystem-audit:audit`: там сверка слоёв, сравнение с GitHub-аналогами и верификация
  каждой находки первоисточником. Ретро может **породить** такой аудит («скелеты
  отстали от манифеста» пришло именно из разбора run) — но не выполняет его само.
- **Закрытый run — read-only.** Ретро не дописывает и не «дочищает» его артефакты:
  исправленная задним числом хроника перестаёт быть свидетельством. Всё, что найдено,
  меняет правила и код, а не прошлый run.
- **Ретро не оценивает людей и агентов.** Единица разбора — цикл и его причина.

## 8. Куда пишется результат

- **Разбор** — `docs/architecture/retro-<project-slug>-<YYYY-MM-DD>.md`: числа из
  команды, пять находок, для каждой — выбранное решение из §6 и его статус. Датированное
  имя обязательно: `tooling/scripts/audit-docs.mjs` не сканирует пути в датированных
  снимках, а разбор законно цитирует каталоги, которые потом уедут в архив.
- **Изменения** — в тех местах, где живёт правило: тест в `runtime/typescript/`, норма в
  `.claude/skills/<skill>/SKILL.md` и её краткой версии, контракт в
  `agent-pack/agent-contracts/`, обёртка в `.claude/agents/`.
- **В чат** — числа, пять находок и что с ними сделано. Не пересказ отчёта.

## 9. Definition of Done

`yarn workflow:retro` прогнан и его вывод приложен · раздел «Чего эти числа не видят»
прочитан и учтён · сработавшие пороги §5 разобраны · находок не больше пяти, каждая
закрыта одним из трёх решений §6 · новый механизм имеет негативный контроль с
фактическим выводом падения · артефакты закрытого run не изменены · разбор записан в
`docs/architecture/retro-<slug>-<date>.md`.
