Ты — оркестратор (главная сессия). Пользователь хочет разобрать завершённый run (триггеры: «сделай ретро», «разбери запуск», «что пошло не так в run», «retro», «ретроспектива»).

Порядок действий:

- Подключи skill `run-retrospective` и работай по нему. Полная процедура, пороги и Definition of Done — `.claude/skills/run-retrospective/SKILL.md`.
- Если `$ARGUMENTS` пуст, выполни `yarn workflow:list` и спроси, какой run разбирать. Не выбирай сам: разбор чужого run — потраченное время.
- Выполни `yarn workflow:retro $ARGUMENTS`. Прочитай раздел «Чего эти числа не видят» **первым**, до таблицы метрик.
- Пройди пороги §5 skill. Каждый сработавший порог даёт кандидата в находки; отбери не больше пяти, приоритет — по цене канала обнаружения (`user_device` дороже всего).
- Закрой каждую находку одним из трёх решений: машинная проверка, норма в skill/контракте, осознанный отказ с причиной. Находка без решения удаляется из отчёта.
- Новый тест или валидатор — только с негативным контролем и фактическим выводом падения.
- **Артефакты закрытого run не редактируй.** Всё найденное меняет правила и код, а не прошлый run.
- Разбор запиши в `docs/architecture/retro-<project-slug>-<YYYY-MM-DD>.md`. Датированное имя обязательно.
- Если находка относится к устройству системы, а не к хронике run («правило заявлено, код его не исполняет»), не разбирай её здесь — назови и предложи `/subsystem-audit:audit`.
- В ответе дай: метрики с фактическими значениями, пять находок с выбранным решением по каждой, изменённые файлы и что осознанно не покрыто.
